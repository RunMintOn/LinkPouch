# 存储与恢复

适用：修改收藏持久化、数据迁移、备份恢复、读写性能，或维护旧收藏。

先读 [ADR-0002](../adr/0002-local-storage-growth-and-recovery.md) 的设计取舍。操作与备份范围见 [README](../../README.md#backup--recovery)，内容墙与导航见[收藏浏览文档](collection-browsing.md)。这里保留维护约束与实验结论，不重复功能说明。

## 维护约束与已验证的坑

- **跨页面写入**：曾复现两条成功返回的修改互相覆盖，页面内部的 Promise 队列不能协调另一个页面或后台。使用 `src/repository.ts` 的写入入口；`updateItem()` 在锁内读取最新记录，`updateItems()` 的变换也必须基于锁内快照并返回新的变更记录对象：实现按引用识别改动，原地修改对象不会形成持久化变更。采集网络请求放在锁外，避免占住写锁。
- **旧数据维护**：`readingItems` 是旧数组迁移输入及 JSON 字段，不再是运行时整库写入入口。补采使用 `updateItem()` 并保持原生命周期字段；旧补采脚本不能直接重跑。来源访问与账号边界见[采集文档](content-capture.md#一次性补采旧-x-收藏)。
- **首次加载同步**：已复现“新页面正在读取旧快照，收到另一页面的更新后，又被旧快照盖回去”。增量同步必须合并加载期间收到的变更。回归在 `scripts/smoke-storage.mjs`，不能只测页面加载完成后的编辑。
- **图片目录重连**：目录标识参与画廊索引匹配；恢复后重选同一文件夹时需要复用备份中的标识。任意生成新标识会使原索引无法匹配，表现为文件仍在但画廊为空。恢复测试包含已有目录与备份目录标识不一致的情况。
- **备份校验**：采集器允许 `data:` 图片地址；不要把图片 URL 校验收窄成仅 HTTP(S)，否则应用自己保存的内容也可能无法恢复。此例已保留在 `src/backup.test.ts`。

## 性能证据

在独立 Chromium profile、离线、1280×900 视口中，对同一历史样本扩容至 10,000 条：

| 测量项 | 整库数组与全量渲染 | 逐条存储与首批渲染 |
| --- | --- | --- |
| 一次备注修改的存储耗时 | 约 629 ms | 约 1.8 ms |
| 导航至卡片完成布局 | 约 5.23 s，全部卡片 | 约 0.32 s，首批卡片 |
| 初始 DOM 元素数 | 约 130,725 | 约 1,332 |

存储耗时为预热后五次测量的中位数，不含 React 刷新；布局是单次观测，不含真实远程图片下载。样本有 344 条，仅 144 条有正文；扩容循环复用其内容、替换 ID，并清空 Trash 标记。它不是当前 live 收藏库，也不能用来预测未来长文章占比增加后的容量。

改动前万条纯搜索计算约 29 ms；改动后初始全库读取仍约 203 ms。此次收益主要来自减少整库写回与 DOM 工作，不是底层存储突然更快。后续先分别测存储、搜索计算、渲染，不能因“搜索慢”就直接加缓存或搜索引擎。

一次性性能脚本和 profile 在 `/tmp`，不是长期依赖。复测复用 `scripts/smoke-storage.mjs` 的离线环境与真实 API 入口，用 synthetic 数据或用户提供的备份扩容；无需访问原站补采，也不提交个人收藏数据。

## 按改动选择验证

| 改动 | 入口及关键行为 |
| --- | --- |
| 单条写入、删除、迁移、恢复 | `src/repository.test.ts`：重叠编辑、删除不复活记录、恢复不被旧写入覆盖、迁移失败保留旧数据、单条编辑不读写全库 |
| 备份格式 | `src/backup.test.ts`：正文与图片索引往返、旧格式兼容、错误字段拒绝、嵌入图片可恢复 |
| 页面与后台写入协调 | `scripts/smoke-extension.mjs`：两个收藏页面与后台同时修改标题、阅读状态和备注，最终全部保留 |
| 存储与恢复集成 | `scripts/smoke-storage.mjs`：迁移、加载中更新、跨批导航、自动备份、轮换、模拟权限/写入失败、目录重连、浏览器启动补写 |

**先构建，再跑浏览器检查。** 存储脚本复制 `dist/` 中的应用，再从源码临时编译测试 API 入口；省略构建会混用旧应用和新 API。临时入口用于避开构建产物的哈希 chunk 名，不是线上扩展的新接口。启动环境见[采集文档](content-capture.md#可重跑的无头验证)。

单元测试的 `src/test/web-locks.ts` 是平台边界 stub，不证明真实的跨页面协调。浏览器检查才覆盖实际 Web Locks、扩展后台及原生文件读写。

## 权限与生效边界

- 目录检查使用 OPFS 原生句柄替代系统选择器；已验证独立浏览器重启后的 OPFS 备份补写，并模拟拒绝权限、写入失败。它不证明 Ego 外部目录授权弹窗或跨重启权限保持正常。
- [Ego 目录重复授权 issue](../../.scratch/reading-queue/issues/01-ego-directory-permission.md) 仍为待确认；不能据上述测试关闭。不要用缓存的“已授权”标记代替浏览器权限检查。
- 构建通过不等于用户当前安装已更新；按 README 的原目录更新方式生效。Ego 与 Chrome 的 profile 数据隔离，相关实测与数据来源要求见[采集文档](content-capture.md#数据与执行边界)。
